# Main architectural decisions

| Decision | Reason | Accepted cost |
|---|---|---|
| Archetype ECS with SoA tables | iteration close to a hand-written SoA | transitions move the entity between tables |
| Memoized `±ComponentId` edges with column mapping | transition with no hash and no allocation | memory per archetype |
| Archetypes never removed | stable pointers, queries without invalidation | empty archetypes remain |
| `detail/` + lint instead of pimpl | hot templates inline | boundary enforced by the lint, not by the compiler |
| Separate template API and `ById` API | the hot path pays no indirection | two implementations to maintain |
| `CommandBuffer` with one transition per entity | cheap batched flush | coalescing complexity (covered by fuzz) |
| Observers run under the iteration lock and change structure through a `World`-owned buffer applied before the operation returns | no observer re-enters a transition in progress; the existing asserts catch a direct change at no new cost | a cascade costs one extra flush per round |
| Observer flags cached in edges and archetypes; implied columns stored in edges | with no observer on a transition the cost stays within noise of none (NF-P4); an implication costs no lookup | all flags recomputed when an observer is registered or removed; `Edge` grows by one vector |
| Loop and every engine rule in C++ | a C++-only game does not end up with an incomplete engine | TS needs the callback |
| A per-engine script invoker set through the C API; the web host installs the JS one | the core knows no environment; a managed client passes its own handle in `userData` | one function pointer and one `userData` per engine; dispatch by `kind` in each client |
| `.oly` as the single source + C++ generator + hash; each client gets generated code | one schema for every environment and language; layout and hash computed once | the TS schema API and the TS generator are gone; `./spur ts` builds `oly-schema` first |
| A plugin `.oly` declares only components, tags and events | a plugin's header is generated once, while action and state ids are `constexpr` values that would depend on each game's install order; events are keyed by C++ type | a plugin cannot bring an action or a state until runtime-resolved handles exist |
| The TS schema is emitted by the game's CMake target (`TYPESCRIPT`), not by a `./spur ts` loop | the plugin list lives in one place (CMake), so the C++ registry and the TS file always hash the same merged schema | `./spur ts` configures a `wasm-games*` preset before `tsc` |
| Column of structs, strided view | does not change the `Table` or the query API | strided accessor in TS |
| `Engine` does not own the `World` | the ECS stays below and independent of the engine | two `Engine`s on the same `World` share the scope tag |
| The `Engine` owns the plugin instances and destroys them in reverse install order | a plugin's state lives in its instance and reaches its systems through `userData`; a game reaches it with `plugin<P>()` | observers belong to the `World`, which outlives the `Engine`, so a plugin's destructor must remove the observers it registered |
| Order bands (`Default`, `Last`) as storage, one vector per phase and band | a plugin system can run after the game's systems of its phase with no branch per system in `runPhase`, and the phase still flushes once | only two bands; inside a band, registration order is the only order |
| `setUpGame`, generated by CMake, replaces `declareSchema` as the game's entry point | one call declares the schema and installs the plugins in dependency order, so no plugin needs a line of game code | `declareSchema` stays, called only by `setUpGame`; a test executable that is not a game defines `setUpGame` by hand |
| `DIMENSION` turns `essentials2d` or `essentials3d` on, and the games do not declare `Position` | one plugin per dimension, so a 2D game pays nothing for quaternions and the components have one definition | a game cannot opt out of `essentials`; parents and non-parents live in different archetypes (the `HasChildren` tag) |
| State scope through an internal tag | cleanup by query, cheap `persist` | twin archetypes with and without the tag |
| Schedule as a min-heap in `app`, not as entities | tasks do not show up in the game's queries | task scope implemented separately |
| Input in its own module, without a platform interface | edge rules testable without `Engine`; the host only pushes events | — |
| C++ first, clients grouped by environment, C++ not a client | the engine is complete in C++; a client only adds language conveniences and each environment has one host | a game in another language depends on the C API, and the guide teaches the concepts in C++ |
| The native host is a library the game calls (`oly::native_host::run`) | `main` is visible, the order is explicit and a headless test needs no second entry point | some repeated code in each game's `main` |
| C API headers as valid C (`.h`) | a C, C#, Rust or Lua client consumes the real ABI | handles need `typedef`s and `struct` tags |
| `@oly/core` without DOM, `@oly/web-host` with DOM | the TS core runs in node, browser and worker | two packages |
| One version for the tag, the `oly-tools` archives, the npm tarballs and the images; `0.x` minors may break | a game pins one number and gets a tested set | no partial release; a breaking change in `0.x` is not signalled by the number |
| The tag is the C++ package and is created last, on the tested commit | a tag pushed before the checks would be a published version that did not pass them; no separate source asset | `FetchContent` at a real tag is first exercised by games, after publishing |
| Releases are cut by hand (`workflow_dispatch`) from `master`, with `dry_run` on by default | the author decides when; a rehearsal costs one click | no release on every push |
| `oly` is a POSIX sh launcher that fetches the tools of the version a game pins; the version's `Spurfile` holds the tasks | no copy of the tasks in a game, so they never drift; the launcher rarely changes | four commands (`new`, `upgrade`, `self-update`, `--version`) live in the launcher and cannot change per version |
| `oly-schema` ships prebuilt in `oly-tools`, linux-x64 static and windows-x64 MinGW static | a host tool with no ABI link to the game; a web game on Windows needs no native compiler to generate the schema | two more binaries to build and test per release |
| `OLY_RELEASE_URL` is the base of every download, with GitHub's layout (`download/v<V>/`, `latest/download/`) | the staged tests and a mirror use the same code path as GitHub, with no test-only branch | a mirror must copy the layout |
| `VERSION` and `oly` are release assets | "the latest version" is one small file `curl` reads, and `self-update` needs no API call or token | two more files in every release |
| `cmake/mingw-w64.cmake` is in `oly-tools` | a Linux game that builds the `.exe` has no engine checkout to take the toolchain file from | the file is copied from `cmake/toolchains/` at packaging |
| Local mode (`OLY_ENGINE_DIR`) replaces tools, source, `oly-schema` and npm packages and edits no file of the game | an engine change shows in a game without a release and without a dirty `package.json` | the npm packages are compiled over the installed tarballs, and `node_modules/.oly-install` marks the platform and mode so that a change reinstalls |
| `OLY_WERROR` is on only when the engine is the top-level project | a game's warnings are the game's own; the engine's `-Werror` must not break a game on a newer compiler | a game gets `-Wall -Wextra -Wpedantic` but not `-Werror` unless it asks |
| `OLY_SCHEMA_TOOL` is an input, and `CMakePresets.json` stays container-only | the game tasks pass the configure options directly, so no preset file is copied into each game | the game `Spurfile` builds the CMake command line |
| `toolchain.env` is the one place for toolchain versions; the Emscripten version must be equal, the others are minimums | the engine is tested with one emsdk, and the image tests set the minimums | the minimums are not bisected, so an older toolchain is untested rather than known to fail |
| The `windows` image takes MinGW from Debian and fails its build below `MINGW_GCC_MINIMUM` | no MinGW pinned from elsewhere | the version follows Debian `trixie` |
| The `wasm` image builds `oly-schema` with emsdk's Clang (`CC=clang`) | Ubuntu's default GCC there is below `GCC_MINIMUM` | the schema tool is built by a different compiler in that image |
| Windows hosts: MSYS2 UCRT64 and Ninja, from Git Bash; no MSVC, no macOS, no PowerShell or `cmd` | one host toolchain to test; CMake's default generator on Windows (Visual Studio) drives neither MinGW nor Emscripten | the guide names the packages, and a reader on another shell is told to use Git Bash |
| Game builds are `Debug` | `OLY_ASSERT` stops a contract violation in a game, as in the engine's debug presets | a game's release build is not one of the tasks |
| The template and the game tasks live in the engine (`templates/game/`, `tools/oly/`), and the template game is minimal | the template is tested by the consumer test at every release and cannot drift from the engine | the repository holds no example game: the engine's test games check the engine at `HEAD`, and only the consumer test, at release, builds a whole game |

The details of each decision are in the module files ([README.md](../../architecture/README.md#index)) and in the specs.
